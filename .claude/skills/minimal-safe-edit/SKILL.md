# Minimal Safe Edit

## 核心原则

- 先分析，再修改，最后测试，禁止盲目写代码。
- 优先复用现有逻辑，采用最小差异。
- 不破坏文件结构、公共接口、数据结构、许可证或第三方代码。
- 保持模块解耦、职责清晰和调用关系可追踪。
- 只在关键边界检测，避免过度防御和重复校验。

## 工作流程

1. 明确需求、验收条件和修改边界。
2. 定位相关文件、函数、模块及调用关系。
3. 分析现有实现，确定最小可行方案。
4. **停点：输出方案声明并等待用户确认，内容包括：**
   - 允许修改的文件列表。
   - 每个文件的具体改动点。
   - 允许新增的文件，如有。
   - 范围外的只读文件。
   - 已验证事实与推测内容。
   - 预计修改规模及预算情况。

   用户确认前，禁止进入下一步。
5. 按确认后的方案实施最小修改。
6. 执行与变更范围匹配的定向测试。
7. 测试失败时，先定位原因，再进行必要修正。
8. 检查最终差异，确认没有无关修改。
9. 汇报修改内容、测试结果和剩余风险。

## 修改约束

默认单次任务预算：

- 修改文件数不超过 3 个。
- 新增文件数不超过 1 个。
- 净增代码行数不超过 80 行，不含测试。

超出预算时必须暂停，说明原因、影响和预计新增内容，并等待确认。

除非用户明确要求，不得：

- 移动、删除或重命名现有文件。
- 修改第三方依赖源码。
- 删除许可证、版权声明或原作者注释。
- 随意改变公共 API、配置格式或核心数据结构。
- 进行无关重构、批量格式化或新增复杂抽象。

优先通过已有调用层、适配层或包装函数实现需求。

## 校验规则

只在以下位置进行必要检查：

- 修改前：确认目标、范围和调用影响。
- 外部边界：处理用户输入、文件、网络、数据库和第三方数据。
- 修改后：执行语法、类型、构建或相关测试检查。

如果数据已由以下机制保证，禁止增加重复的运行时检查：

- 类型系统或编译期检查。
- 框架输入校验。
- 可靠的内部调用，且调用方已完成校验。
- 项目已有的统一校验层。

新增校验前必须说明：

1. 是否与现有机制重复；
2. 如果不重复，现有流程的缺口是什么；
3. 为什么当前修改需要补足该缺口。

## 解耦与错误处理

- 保持函数单一职责，避免循环依赖和跨层直接调用。
- 修改函数签名时，检查相关调用方。
- 遵循项目已有的错误处理方式。
- 不吞掉异常，不用捕获所有异常掩盖问题。
- 无法安全判断时，停止修改并报告具体原因。

## 输出要求

完成后说明：

- 修改了哪些文件及具体内容。
- 是否改变公共接口或调用关系。
- 执行了哪些验证。
- 新增校验是否存在及其必要性。
- 是否存在未处理风险。

不得将未执行的测试描述为已执行。
